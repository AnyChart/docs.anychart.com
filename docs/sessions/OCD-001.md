## Research Findings — Summary

### AnyChart Ecosystem (Agent 1)

**Key discoveries:**
- **Production docs branch is `v8`**, not master — head equals latest release tag 8.14.1
- **9 stale DVF branches** still exist in docs repo (DVF-2409 through DVF-4710) — never cleaned up
- **CDN publishes branch builds** automatically: `cdn.anychart.com/releases/DVF-XXXX-description/js/...`
- **`{{branch-name}}`** template variable is the coupling mechanism across repos
- **`config.toml`** holds version numbers, `release-version.sh` does the replacement at release
- **No GitHub Actions** in any repo — CI is internal (likely Jenkins/TeamCity)
- **v7 docs served at `/v7/` path** — confirming historical path-based versioning

### Versioning Approaches (Agent 2)

**6 approaches evaluated, clear winner: Multi-Deployment with different `baseUrl`**

| Approach | Verdict |
|----------|---------|
| Docusaurus built-in versioning | REJECTED — `routeBasePath: '/'` bug, single `ANYCHART_VERSION` for all versions |
| **Multi-Deployment (different baseUrl)** | **RECOMMENDED** — independent builds, perfect version coupling, zero production risk |
| Multi-instance plugin | REJECTED — config changes per branch, single preprocessor pass |
| Spectro Cloud branch-orchestrator | REJECTED — fragile shell scripts, same single-build limitations |
| Reverse proxy stitching | Variant of recommended approach |

**Why multi-deployment wins:**
- Each branch build gets its own `ANYCHART_VERSION` → samples/CDN links are correct
- `routeBasePath: '/'` stays untouched — no known Docusaurus bugs triggered
- Zero risk to production — branch builds are isolated directories
- Cleanup is `rm -rf` — no build system state to manage
- Industry standard (how Vercel/Netlify/Read the Docs work)

### CI/CD Patterns (Agent 3)

**Recommended architecture: 3 GitHub Actions workflows**

1. `deploy-branch.yml` — triggers on push to `DVF-*`, builds with modified `baseUrl`, deploys via rsync
2. `deploy-production.yml` — triggers on push to main/develop, deploys root site
3. `cleanup-branch.yml` — manual dispatch + optional scheduled cleanup

**Key infrastructure:**
- Atomic deployment via rsync to temp dir + mv swap
- `manifest.json` on VPS tracks deployed branches (with `flock` for concurrency)
- nginx `location ^~ /DVF-` prefix match serves branch builds
- SSH Ed25519 key with restricted shell for security

## Decisions Made

| Decision | Rationale |
|----------|-----------|
| Multi-deployment approach for versioning | Only approach that correctly couples `ANYCHART_VERSION` per branch; zero production risk; proven industry pattern |
| Path-prefix URL scheme (`/DVF-5000/Quick_Start`) | Main URLs stay clean, matches old staging pattern, simple nginx routing |
| Full site copy per branch (not changed-pages-only) | No broken internal links within branch versions |
| CDN coupling (branch docs use branch CDN build) | Required for samples to work with in-development library features |
| Manual cleanup of branch versions | Keeps shared links alive after merge; no accidental deletion |
| Subtle version indicator (not prominent dropdown) | Branch versions are secondary; main docs should feel clean |
| OCD session system adapted from Rolodex project | Structured handoff between sessions; not tied to git branching (yet) |
| API reference migration deferred to later phase | Seal docs end-to-end first |
