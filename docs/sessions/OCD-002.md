## Work Streams

### WS-1: Staging Infrastructure
**Goal:** Get `docs.anychart.stg` serving a Docusaurus build from the `develop` branch.

- GitHub Actions workflow: `deploy-staging.yml` — build on push to develop, deploy via rsync
- GitHub Actions workflow: `deploy-production.yml` — build on push to v8/main, deploy to production
- VPS nginx config for staging domain
- SSH key setup and GitHub secrets
- Verify staging server (`104.236.66.244`) is available

### WS-2: Auth-Gated Staging Access
**Goal:** Only AnyChart org members / whitelist can view staging.

- Extend existing Express server with staging-specific auth middleware
- GitHub OAuth check: is user in AnyChart org? (GitHub API)
- Whitelist fallback for external collaborators
- Login page / redirect for unauthenticated users

### WS-3: Diff Highlighting System
**Goal:** Staging visually shows what changed vs production and which DVF ticket introduced each change.

- Build-time diff script: compares staging branch vs production branch
- Git blame attribution to DVF tickets
- Diff manifest JSON output
- React component for inline highlighting
- Staging banner: ticket list, changed page count

### WS-4: Branch-Aware Edit Flow
**Goal:** "Suggest Change" on staging targets the staging branch; editor shows context.

- Detect which deployment context the editor is running in (prod vs staging)
- Route PR to correct base branch
- Editor UI: "You are editing the staging branch. Switch?"
- Edit flow for production stays as-is (targets develop)

### WS-5: Cross-Repo Automation
**Goal:** Push DVF-* to AnyChart/AnyChart → auto-create matching branch in docs repo.

- GitHub Actions workflow in AnyChart/AnyChart repo
- Uses GitHub API to create branch in docs.anychart.com
- Requires PAT or GitHub App token with cross-repo permissions

### WS-6: Version Archives
**Goal:** Mechanism to snapshot a major version as `/vN/` archive.

- Script: build current docs with `baseUrl: '/vN/'` and deploy to subdirectory
- nginx config for `/v7/`, `/v8/` paths
- "Looking for older versions?" link in footer/navbar
- One-time operation per major release — not automated

## Agent Architecture

Inspired by the Morwen/Lyra multi-agent pattern: clear domain ownership, shared state, orchestrator coordination.

### Agents

| Agent | Domain | Owns | Does NOT touch |
|-------|--------|------|----------------|
| **Infra Agent** | CI/CD & deployment | `.github/workflows/`, nginx configs, deployment scripts | Application code, UI components |
| **Backend Agent** | Server, auth, API | `server/`, auth middleware, API routes | UI components, CSS, Docusaurus config |
| **Frontend Agent** | UI, components, Docusaurus | `src/`, `docusaurus.config.ts`, theme components | Server code, workflows, deployment |
| **Diffing Agent** | Diff system | `scripts/diff-*`, diff manifest, build-time tooling | UI components, server code |

### Orchestration

- **This session (OCD-002)** produces the plans
- **Agents execute independently** — each gets a plan file with clear inputs/outputs
- **Shared state:** `docs/sessions/OCD-002.md` tracks progress across agents
- **No COMMS.md needed** (single-session execution, not concurrent terminals)
- **Integration points** are explicit: "Infra Agent deploys → Frontend Agent can test staging banner"

### Execution Order

```
Phase 1 (parallel):
  ├─ Infra Agent: WS-1 (staging infrastructure)
  └─ Frontend Agent: WS-3 (diff highlighting component, can develop locally)

Phase 2 (after WS-1 staging is live):
  ├─ Backend Agent: WS-2 (auth-gating)
  └─ Frontend Agent: WS-4 (branch-aware edit flow)

Phase 3 (after core is stable):
  ├─ Infra Agent: WS-5 (cross-repo automation)
  └─ Infra Agent: WS-6 (version archives mechanism)
```

## Decisions Made

| Decision | Rationale |
|----------|-----------|
| 4-agent architecture | Clean domain separation; agents can work in parallel without conflicts |
| Phase-based execution | Some work streams depend on others (auth needs staging to exist first) |
| No fictional personas | Unnecessary for this project; clarity over flavor |
| Plans as files, not live comms | Single orchestrator session, not concurrent terminals |
